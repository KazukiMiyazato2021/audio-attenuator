# 仮想デバイスの遅延申告

アプリは出力デバイスの `kAudioDevicePropertyLatency` を読み、**映像側を遅らせて
リップシンクを取る**。

仮想デバイスは玄関口にすぎず、実際に音が出るのはミキサーが再生している先の
デバイスである。そちらが大きな遅延を持つ場合、**仮想デバイスが 0 を申告すると
アプリは「音声は即座に出る」と信じて補正しなくなり、音だけが映像から遅れる。**

## 実例

| 構成 | 遅延の体感 | 理由 |
|---|---|---|
| Bluetooth 直結 | なし | アプリがデバイスの 233ms を読んで映像を補正 |
| 仮想デバイス + 内蔵スピーカー | なし | スピーカー自体の遅延が 19 フレーム(0.4ms)で無視できる |
| 仮想デバイス + Bluetooth | **200〜400ms** | アプリには仮想デバイスの 0 しか見えない |

RY-WH02 の申告値は `Latency out=10284` フレーム。44100Hz なので 233ms。

**この遅延は短縮できない。** 正しく申告してアプリに補正させるのが解決策。

## 対処

ミキサーが出力先デバイスの遅延を測り、自パイプラインのレートに換算し、
自身のバッファ分を足してドライバへ渡す。ドライバはそれをデバイスの遅延として申告する。

出力先デバイスを切り替えるたびに再計算・再通知すること。

## ドライバへ値を渡すまでの障壁

3つの仕様が順に立ちはだかる。詳細は
[[AudioServerPlugIn のカスタムプロパティ]] を参照。

1. HAL は `kAudioDevicePropertyLatency` へのクライアント書き込みを
   ドライバへ届く前に拒否する(`'nope'`)
2. カスタムセレクタは `kAudioObjectPropertyCustomPropertyInfoList` で
   宣言しない限り転送されない(`'who?'`)
3. カスタムプロパティは `CFString` か `CFPropertyList` しか運べない

## 確認方法

```
[mixer] published latency: device 10284 frames @ 44100Hz + pipeline 1280
        = 12473 frames (260ms), status 0
```

`status 0` を確認したうえで、デバイス側の申告値も読み戻す。

```
Attenuator Device Latency: out=12473 in=12473
```

再生中のアプリは起動時に遅延値を読んでいるため、**確認時は再生し直す**か
タブを再読み込みすること。
