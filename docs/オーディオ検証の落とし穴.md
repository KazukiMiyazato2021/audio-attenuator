# オーディオ検証の落とし穴

このプロジェクトで発生した不具合は、**ほぼ全てが検証条件の偏りによる見逃し**だった。
個々の不具合そのものより、この傾向の方が再発しやすい。

## 内蔵スピーカーだけで検証していた

内蔵スピーカーは 48kHz に対応し、遅延も 0.4ms と無視できる。
**たまたま問題が表面化しない条件**だった。

Bluetooth を試すまで、以下の3件がすべて隠れていた。

- [[出力デバイスのサンプルレートを強制しない]] — 48kHz 対応デバイスでは無害
- [[仮想デバイスの遅延申告]] — 遅延 0.4ms のデバイスでは影響が出ない
- [[リングバッファの遅延管理]] — 切り替え時の溜まりが小さく気づかない

## 合成音だけで検証していた

自前のトーン生成プロセスはデバイスへ直接書き込む。実アプリは macOS の
デフォルト出力経由という**別の経路**を通る。

またトーン生成プロセスは単一の安定したプロセスだが、実アプリ(特にブラウザ)は
複数プロセスを持つ。→ [[オーディオプロセスのグループ化]]

## CLI だけで検証していた

ターミナルはマイク権限を持っているため、**CLI では完璧に動いて見えた**。
パッケージ化して launchd から起動する実際の経路で初めて権限不足が露呈した。
→ [[TCC 責任プロセス]]

## 教訓

「動いた」と判断する前に、**実際の使用条件と一致しているか**を確認する。

| 検証でやりがち | 実際の使用条件 |
|---|---|
| 内蔵スピーカー | Bluetooth・USB DAC など 48kHz 非対応もある |
| 自作のテスト音源 | ブラウザ・音楽アプリ |
| ターミナルから実行 | .app を launchd 起動 |
| 単一プロセス | ヘルパープロセスを持つアプリ |

## 実務上の注意

### 測定値をログに出す

このプロジェクトでは各経路の実測フレームレート、リングバッファの滞留量、
ピークレベル、アンダーラン数をログに出すようにした。
**耳で気づく前に数値で分かる**ことが切り分けを大きく速くした。

バックグラウンドで動くエージェントは状態が全く見えないため、
診断ログが無いと調査が始められない。

### テスト音源は単一の安定したプロセスにする

タップは特定のプロセスオブジェクトに紐付く。ループで `afplay` を繰り返すと
インスタンスごとに別プロセスになり、新しいものがタップ対象外になる。
ミュートが漏れているように見えて紛らわしい。

長い音源を1回再生する形にする。

### 検証スクリプトは状態を戻す

エージェントを止めて検証するスクリプトは、終了時(異常終了・中断を含む)に
必ず元に戻すこと。止めたままにすると音が出なくなり、原因も分かりにくい。

### macOS に `timeout` は無い

GNU coreutils の `timeout` は存在しない。無いコマンドを呼ぶとスクリプトが
何も実行せずに終わり、**テストが通ったように見える**。
バックグラウンド実行とウォッチドッグで代替する。

### 出力のバッファリング

Swift の `print()` はファイルへリダイレクトするとブロックバッファリングされ、
プロセスを kill すると失われる。`setvbuf(stdout, nil, _IONBF, 0)` で無効化する。
