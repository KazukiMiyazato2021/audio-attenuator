# リングバッファの遅延管理

**一時的に溜まった分は、放置すると永久に残る。**

生産側と消費側が同じレートで動くパイプラインでは、いったん溜まった差分を
減らす仕組みが無い限り、その分がそのまま恒久的な遅延になる。

## 溜まる場面

| 場面 | 実測 |
|---|---|
| Bluetooth への出力開始時 | 403ms |
| 出力デバイス切り替え直後 | 105ms |

キャプチャはデバイスを開いた瞬間から動き始めるが、出力側は準備ができるまで
引き取りを始めない。その間に溜まった音声は**まだ誰も聞いていない**ため、
保持する価値がない。

## 対処

### 1. IO 開始直後に一度捨てる

出力が動き出した最初のコールバックで、目標値を超える分を破棄する。
これが根本対処になる。

読み取り位置を動かす操作なので、**消費側(レンダーコールバック)から行うこと**。
制御スレッドから触ると読み取り位置の競合になる。フラグを立ててコールバック側で
処理させる。

### 2. 平常時は少しずつ削る

目標を超えている間、毎コールバック数フレームだけ捨てる。1 バッファの 1% 未満なら
聴感に影響しない。数千フレームを一度に捨てると明確な音飛びになる。

### 3. 大きく外れたときだけ一括で捨てる

閾値(64ms 程度)を超えたら一気に目標まで戻す。一瞬の不連続の方が、
何十秒も遅延を抱えるよりましという判断。

削る速度が遅すぎると解消に時間がかかる。毎コールバック 4 フレームでは
5000 フレームの解消に約 20 秒かかり、「切り替え直後だけ遅い」という症状になる。

## 調整は耳ではなく実測で

遅延を詰めすぎると**アンダーラン(バッファ枯渇による音切れ)**に変わる。
音切れの方が遅延より不快なので、アンダーランのカウンタを用意して
0 件であることを確認しながら詰める。

```
[mixer] levels: ... | backlog fb=979 (20ms) ... | underruns=0
```

## 実績値

- 目標: 768 フレーム(16ms)
- 一括削除の閾値: 3072 フレーム(64ms)
- 起動直後から 4〜15ms で安定、アンダーラン 0 件

## ドライバ内部のリングバッファ

ドライバ内で Output ストリームから Input ストリームへ渡す場合も同じ問題がある。

読み取り位置を書き込み位置と**同じ**にすると、まだ書かれていない領域、
すなわち一周前の最も古いデータを読むことになる。65536 フレームのバッファなら
1.37 秒の固定遅延になる。書き込み位置の**少し手前**に置くのが正しい。

余裕は IO 周期 1 つ分(512 フレーム = 11ms)で足りる。ここはパイプライン全体が
背負う遅延なので、必要以上に取らない。
